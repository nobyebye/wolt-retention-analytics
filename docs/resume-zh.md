# 简历可用内容

## 精简版

**Wolt 业务场景用户留存与复购分析系统｜独立项目**

技术栈：MySQL 8、Python、SQL、Streamlit、Docker Compose、GitHub Actions

- 基于 Wolt 官方公开模拟数据，整合 29.87 万条源记录，构建包含 7.13 万名用户、28.86 万条购买事件的分析数据集，完成原始数据、用户维度、购买事实及指标汇总建模。
- 建立按首购月份和业务线划分的同期群留存、30 天复购及跨业务线购买指标，处理观察窗口截尾、零复购用户分母和平台/同线留存口径差异。
- 识别并隔离 10,145 条缺少首购锚点的购买记录，实现参数化批量导入、事务回滚、幂等刷新和 7 项数据质量检查；通过 13 项单元及 MySQL 集成测试。
- 开发可筛选的留存看板与 CSV 导出，提供 MySQL 执行计划和复合索引对比实验，形成可复现的分析报告及部署配置。

可选技术量化句（必须保留测试条件）：在 28.86 万条事实记录的本机热缓存实验中，对同一用户及日期区间的计数查询，通过复合覆盖索引将 7 次运行的耗时中位数从 40.60 ms 降至 0.35 ms，核验两种查询均返回 203 条匹配记录。该结果不是整体系统提速或生产 SLA。

## 面试 60 秒介绍

我做了一个以芬兰创立的 Wolt 为业务背景的独立分析项目，使用它官方公开的模拟数据。目标是比较餐饮和零售首购用户的留存和复购。
最重要的发现不是业务结论，而是两份表并不能直接关联：购买表里有一万多条记录找不到首购用户，且两份表的订单 ID 没有重合。
我保留了原始数据，把首购表作为 cohort 锚点，对未知用户隔离；同时保留不复购的用户作为分母，将观察不完整的月份显示为空值。
实现上使用 MySQL 分层表和 SQL 汇总、Python 批量导入、事务刷新与质量闸门，再通过 Streamlit 展示。
测试覆盖了未完成月份、零返回用户、跨业务线购买和中途失败回滚，所有结果都能重新运行验证。

## 面试追问准备

- 为什么 M1 不等于 30 天复购？M1 是下一个日历月，30 天指标是每名用户的固定观察窗口。
- 为什么不删掉没复购的人？他们是 cohort 分母的一部分，删除会高估留存。
- 0 与 NULL 的区别？0 表示完整观察却无人返回，NULL 表示没有完整观察资格。
- 怎么保证重复运行不重复？在专属数据库中互斥执行，在同一事务内 DELETE + INSERT 全量刷新。
- 如何证明失败不损坏报表？集成测试在 SQL 阶段故意失败，断言上次事实快照仍保留。
- 能不能说帮助 Wolt 提高留存？不能。这里是公开模拟数据的独立分析，没有真实上线或实验收益。
